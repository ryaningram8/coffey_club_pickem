# Flutter apps (web + mobile + shared package)

## What it is

[Flutter](https://flutter.dev) is Google's UI toolkit — one Dart codebase compiles to native mobile apps (iOS/Android) and to a web app (compiled to JS/Wasm), sharing nearly all UI and logic code. This project uses that to maintain one pick'em app that runs both as a website and as phone apps.

## How it works — the three-package split

```
apps/web/       — Flutter web entrypoint only (main.dart, web-specific config)
apps/mobile/    — Flutter mobile entrypoint only (main.dart, android/, ios/)
packages/coffey_ui/  — ALL shared code: everything both apps actually use
```

Per CLAUDE.md, `apps/web` and `apps/mobile` are intentionally thin — they exist only because web and mobile need slightly different bootstrapping (see below), not because they have different features. Every screen, BLoC, model, and API call lives in `packages/coffey_ui`, which both `apps/web` and `apps/mobile` depend on as a local package (see their `pubspec.yaml`).

`apps/web/lib/main.dart` and `apps/mobile/lib/main.dart` are nearly identical: initialize Firebase (wrapped in a `try/catch` so a missing Firebase config doesn't crash the whole app — see [11-firebase-fcm.md](11-firebase-fcm.md)), then `runApp(const CoffeyApp())`, where `CoffeyApp` itself lives in `coffey_ui`.

## How it works — inside coffey_ui

Four architectural layers, each with a hard rule from CLAUDE.md:

- **`blocs/`** — state management, using the [BLoC pattern](https://bloclibrary.dev) (`flutter_bloc`). BLoC for complex multi-event state (auth, pick sheet, live results), Cubit for simple toggles (notification prefs). One BLoC per feature domain, never shared across unrelated screens. Events are past-tense (`PicksLoaded`), states are `freezed` unions (`initial`/`loading`/`success`/`failure`).
- **`repositories/`** — the only layer allowed to make HTTP calls, via Dio (HTTP client) + Retrofit (generates typed API-call methods from annotated interfaces, so you write `Future<Week> getWeek(String id)` and Retrofit generates the actual `dio.get(...)` call). BLoCs never call Dio directly — always through a repository.
- **`models/`** — data classes, generated by `json_serializable` (no hand-written `fromJson`/`toJson`) and `freezed` (immutable classes, union types).
- **`screens/` / `widgets/`** — UI. Screens are thin — mostly `BlocBuilder`/`BlocListener` wiring — with actual reusable UI broken out into `widgets/`.

Routing: a single `AppRouter` class using [GoRouter](https://pub.dev/packages/go_router), with named routes (`AppRoutes`) — no inline string literals for paths. `AppRouter`'s `redirect` handles auth guards (e.g. bouncing an unauthenticated user to `/login`) and deep links like `/week/:id` straight to the pick sheet.

Auth token storage differs by platform, deliberately: `flutter_secure_storage` (OS keychain) on mobile, plain `SharedPreferences` on web — a comment in `token_storage.dart` explains that web's "secure" storage layer proved unreliable across dev sessions and doesn't add real security on web anyway (browsers don't have a keychain-equivalent Flutter can hook into the same way).

## Where it runs

- **Mobile**: compiled to a real Android/iOS app, installed on a device or emulator. Talks to the backend over HTTPS via `APP_URL`.
- **Web**: compiled by `flutter build web` into static JS/HTML/CSS/Wasm, served by Nginx as static files (see [08-nginx.md](08-nginx.md)) — it is *not* a Node/Dart server running anywhere, just static assets.
- **Dev**: `flutter run` (mobile, needs a connected device/emulator) or `flutter run -d chrome` (web, opens a dev server with hot reload) — both point at whatever backend URL is configured for that build (typically `http://localhost:4000` in dev).

## How to view it

- `flutter run -d chrome` from `apps/web/` — fastest way to see the app in a real browser with hot reload.
- `flutter analyze packages/coffey_ui apps/web apps/mobile` — static analysis across all three; this was run clean this session.
- `flutter build web` from `apps/web/` — produces the production static build at `apps/web/build/web/`, which is what Nginx expects to find. **This hasn't been run yet** — that directory doesn't currently exist, which is why the Nginx container can't serve anything real right now.
- Mobile: `flutter run` with a device connected, or an emulator/simulator running (Android Studio / Xcode tooling, not covered here).
