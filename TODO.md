## Multi-pool support

Started 2026-08-14: added a `SeasonMembership` join table + `/invitations` routes so a user can belong to more than one concurrent pool/season (e.g. a preseason test pool now, the main season later, or two genuinely separate friend groups run at the same time). `getActiveSeason`/`getCurrentWeek`/`submitPicks` are scoped to membership now. Auditing for "everything needs to be tied to seasonId" turned up more places than just those — tracked here.

- [x] `Game.espnGameId` was globally unique in the DB, and [week.service.ts](backend/src/services/week.service.ts)'s `assignGames` upserted by that key alone — meaning if two concurrent pools' commissioners both selected the same real-world game, the second pool's publish would silently steal/reassign that `Game` row (and its `weekId`) from the first pool, corrupting both weeks. Fixed: uniqueness is now scoped to `(weekId, espnGameId)` (migration `20260814203655_scope_game_espn_id_per_week`); verified live by assigning the same `espnGameId` into two different pools' weeks and confirming both persisted as independent rows.
- [x] `schedulePickReminders` in [notification.service.ts](backend/src/services/notification.service.ts:174) queried `prisma.user.findMany({})` with no filter at all — every publish of a week in *any* pool scheduled a pick-reminder job for *every* user in the whole system, not just that pool's members. Fixed: now takes `seasonId` and filters to users with a `SeasonMembership` for it. Verified live — published a week in a pool with exactly one member and confirmed only one BullMQ job was queued (for that member), not one per every seeded user.
- [x] `broadcast()` in [notification.service.ts](backend/src/services/notification.service.ts) sent to every user in the system, unscoped by pool. Resolved as part of the pool-scoped-roles rework below: `seasonId` is now optional on `POST /admin/broadcast` — admin can omit it (everyone, unchanged) or supply one (scoped to that pool); a non-admin pool commissioner must supply their own pool and can't omit it. Verified live: admin-no-seasonId reaches everyone, a pool commissioner scoped to their own pool succeeds, the same commissioner omitting `seasonId` or targeting a different pool both 403.
- [x] Read-side endpoints didn't check pool membership at all — any authenticated user could view any pool's data by ID regardless of whether they'd joined it: `GET /weeks/:id`, `GET /weeks/:id/picks/summary`, `GET /weeks/:id/standings`, `GET /seasons/:id/standings`. Fixed: new `requirePoolMember` primitive in [middleware.ts](backend/src/lib/middleware.ts) (admin bypasses, otherwise requires *any* `SeasonMembership` — player or commissioner — unlike `requirePoolCommissioner` which requires the commissioner role specifically), wired into all four. Verified live: created a pool Alice isn't a member of, confirmed all four routes 403 her for it while admin still sees everything and her own pool is unaffected.
- [x] Commissioner/admin `role` was global on `User`, not per-pool — any global commissioner could edit *any* pool's weeks/games, even ones they weren't a member of. Resolved below (pool-scoped-roles rework) — see that section for the full writeup.
- Note, not a bug: `Team` is intentionally global/shared across all pools (real-world teams like "Chiefs" shouldn't be duplicated per pool) — confirmed this is correct as-is, not an oversight.
- [~] Invite-management screen (Flutter) — `InviteManagementScreen` exists and works, but its entry point (mail icon in the Commissioner AppBar) is now stale: `POST`/`GET /invitations` became admin-only in the roles rework below, so a non-admin commissioner would see the icon and get a 403 tapping it. Needs to move to the admin-only Home header — tracked as part of stage 4 below, not fixed yet.
- [x] Pool switcher — superseded by the fuller "pool-scoped roles" plan below, which folds the switcher in as stage 3 (the header pool-selector was always going to be needed to know "which pool's commissioner dashboard am I even looking at" once commissioner became per-pool).

### Pool-scoped roles (started 2026-08-14)

Bigger rework, agreed in chat before starting: `admin` stays a single global flag (applies to every pool automatically, including ones created later); `player`/`commissioner` become per-pool (`SeasonMembership.role`), so e.g. Alice can commission Pool X while just playing in Pool Y. 4 stages, checking in after each:

- [x] **Stage 1 — schema + authorization.** `User.role` (enum) → `User.isAdmin` (boolean); new `PoolRole` enum (`player`/`commissioner`) on `SeasonMembership.role`; migration `20260814221151_pool_scoped_roles` (backfilled the one existing admin correctly, verified via `psql`). New authorization primitives in [middleware.ts](backend/src/lib/middleware.ts): `requireAdmin()`, `requirePoolCommissioner(getSeasonId)` (admin bypasses; otherwise resolves the pool via params/body/a week-or-game lookup and checks `SeasonMembership.role`), `requireAnyCommissioner()` (for the one pool-agnostic route, `GET /games/available`). Rewired: season/week/game update+create routes, payouts, invitations (→ admin-only), broadcast (optional `seasonId`, admin-only-if-omitted). Verified live end-to-end: a plain player 403s everywhere commissioner-gated; promoted to commissioner of one pool via direct SQL (no promote-endpoint yet — that's stage 2), confirmed access opens for *that* pool only and nothing else, confirmed still not admin (invitations still 403). Also had to fix `UserModel`/`home_screen.dart` on the Flutter side (`role` → `isAdmin`) since the login response shape changed — otherwise login would have broken outright; `isCommissioner` on Home is a **temporary stopgap** (`isAdmin` only) until stage 3 replaces it with a per-selected-pool check, so a non-admin commissioner currently won't see the Commissioner entry point at all.
- [x] **Stage 2 — new admin endpoints.** New `admin-users.routes.ts`/`user-management.service.ts`, all `requireAdmin()`-gated: `GET /admin/users` (every user + their per-pool memberships/roles), `PUT /admin/users/:userId/memberships/:seasonId` (change role), `DELETE /admin/users/:userId/memberships/:seasonId` (remove from pool). Verified live end-to-end through the real API (not manual SQL this time): promoted Alice to commissioner via the endpoint, confirmed she could immediately manage that pool; removed Bob from the pool, confirmed his `/seasons/active` correctly 404s with no pools left; double-remove correctly 404s; a non-admin pool commissioner still gets 403 on `/admin/users`. Test data restored to baseline afterward.
- [x] **Stage 3 — Flutter pool switcher.** Backend: new `GET /seasons/mine` (a user's own pools + their role in each — `season.service.ts`'s `listMySeasons`, explicit JS status-priority sort like `getActiveSeason`, not an `orderBy` on the enum); `GET /weeks/current` now requires `?seasonId=` and is scoped to that one pool instead of guessing across every pool a user belongs to. Flutter: new `SelectedPoolCubit` (provided at the app root in `app.dart`, loaded/reset off the `AuthBloc` stream, persists the selection via `SharedPreferences`) backing a new header `PoolSwitcherBar` widget — shows the current pool, a bottom-sheet picker for the rest, and a "Join another pool" action that redeems a code via the (previously built but never wired-in) `POST /invitations/:code/redeem`. Rewired `HomeHeroCubit` (now takes `seasonId`), `CommissionerBloc` (now takes the already-known `SeasonModel` instead of re-resolving "the active season" — also let the now-unreachable `CommissionerState.empty()` variant get removed), and `SeasonStandingsScreen` to all use the selected pool. This replaces stage 1's temporary `isAdmin`-only Commissioner-entry stopgap with a real per-pool check (`isAdmin || selectedPool.myRole == 'commissioner'`). Verified live: `/seasons/mine` reflects a promotion to commissioner correctly; admin's `/seasons` (unchanged) carries no `myRole`; the full mint-invite → redeem → appears-in-`/seasons/mine` loop works exactly as the new "join another pool" dialog will drive it. `flutter analyze` clean across `coffey_ui`/`web` (mobile's one error is the pre-existing unrelated stub test file). Not interactively verified in-browser — same standing environment gap as the invite-management screen (spec.md Phase 4). Found in passing, not fixed (pre-existing, app-wide, not introduced by this work): a missing/invalid required query param or body field returns `500` instead of `400` everywhere in this backend — Fastify has no error handler translating a thrown `ZodError` to a 4xx.
