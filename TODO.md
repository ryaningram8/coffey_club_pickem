## Security (self-hosting hardening)

- [x] `postgres`/`redis` ports in [docker-compose.yml](docker-compose.yml) — were published with the bare `"5432:5432"`/`"6379:6379"` shorthand, which Docker binds to `0.0.0.0` (all interfaces) by default, so both were reachable from any device on the LAN despite the "local dev only" comment. Fixed: bound to `"127.0.0.1:5432:5432"`/`"127.0.0.1:6379:6379"` instead of removing the publish outright, since `npm run dev` (local dev, environment 1) connects via `localhost` and still needs it; the containerized `api` service was never affected either way since it reaches both over Docker's internal network by service name. - [x] Add `@fastify/rate-limit` to `/login`, `/signup`, `/google` in [auth.routes.ts](backend/src/routes/auth.routes.ts) — previously zero throttling, so credential stuffing on `/login` and invite-code brute-forcing on `/signup` were both wide open. Installed `@fastify/rate-limit@9.1.0` (pinned — v10+ requires Fastify v5, this project is still on v4). Registered globally in [server.ts](backend/src/server.ts) with a generous default (200/min/IP, a DoS safety net) plus stricter per-route overrides: `/login` and `/google` 10/min, `/signup` 5/10min (invite codes are guessed rarely, not a high-frequency legitimate action). Deliberately used the plugin's in-memory store rather than a Redis-backed one — `redis.ts` already documents avoiding a standalone `ioredis` instance due to a type conflict with BullMQ's bundled copy, and with only one API instance running there's no multi-instance state to share, so reintroducing that conflict wasn't worth it. Verified live: 15 rapid `/login` attempts → first 10 pass through (401, wrong password) then 429 with correct `Retry-After`/`X-RateLimit-*` headers; `/signup` independently trips at 5; unrelated routes (`/health`) unaffected.
- [x] Fix web refresh-token storage — was plain `localStorage` (via `SharedPreferences`) on web, holding a 30-day JWT any XSS bug could read directly and reuse for a month. Chose the httpOnly-cookie fix over just shortening the lifetime (the other option this item originally named) since only the cookie actually stops the read; a shorter lifetime just shrinks the abuse window. Backend ([auth.routes.ts](backend/src/routes/auth.routes.ts), `@fastify/cookie@9.4.0` — pinned like `@fastify/rate-limit`, v10+ needs Fastify v5): `/login`/`/signup`/`/google`/`/refresh` now also set the refresh token as `HttpOnly; Secure(!isDev); SameSite=Strict; Path=/` alongside the existing JSON-body token (mobile's contract is unchanged — Dio has no cookie jar configured so it just ignores the cookie); `/refresh` now accepts the token from either the body (mobile) or the cookie (web); new `POST /auth/logout` clears the cookie, since nothing client-side can touch an HttpOnly cookie and there's no server-side token revocation otherwise. `Path=/` was a deliberate choice over a narrower `/auth` — local dev hits the backend directly with no prefix while the containerized stack goes through nginx's `/api/` proxy (which strips the prefix before the backend ever sees it), and Set-Cookie `Path` is matched against what the *browser* requested, so one path value has to work in both shapes. Flutter: [token_storage.dart](packages/coffey_ui/lib/src/services/token_storage.dart) now skips persisting the refresh token on web entirely (`kIsWeb` branch in `saveTokens`); [api_client.dart](packages/coffey_ui/lib/src/services/api_client.dart)'s interceptor always attempts refresh on web (no body — relies on the browser auto-attaching the cookie via `withCredentials`) instead of first checking local storage; `AuthRepository.logout()` now also calls the new endpoint (best-effort). ## Multi-pool support

Started 2026-08-14: added a `SeasonMembership` join table + `/invitations` routes so a user can belong to more than one concurrent pool/season (e.g. a preseason test pool now, the main season later, or two genuinely separate friend groups run at the same time). `getActiveSeason`/`getCurrentWeek`/`submitPicks` are scoped to membership now. Auditing for "everything needs to be tied to seasonId" turned up more places than just those — tracked here.

- [x] `Game.espnGameId` was globally unique in the DB, and [week.service.ts](backend/src/services/week.service.ts)'s `assignGames` upserted by that key alone — meaning if two concurrent pools' commissioners both selected the same real-world game, the second pool's publish would silently steal/reassign that `Game` row (and its `weekId`) from the first pool, corrupting both weeks. Fixed: uniqueness is now scoped to `(weekId, espnGameId)` (migration `20260814203655_scope_game_espn_id_per_week`); verified live by assigning the same `espnGameId` into two different pools' weeks and confirming both persisted as independent rows.
- [x] `schedulePickReminders` in [notification.service.ts](backend/src/services/notification.service.ts:174) queried `prisma.user.findMany({})` with no filter at all — every publish of a week in *any* pool scheduled a pick-reminder job for *every* user in the whole system, not just that pool's members. Fixed: now takes `seasonId` and filters to users with a `SeasonMembership` for it. Verified live — published a week in a pool with exactly one member and confirmed only one BullMQ job was queued (for that member), not one per every seeded user.
- [x] `broadcast()` in [notification.service.ts](backend/src/services/notification.service.ts) sent to every user in the system, unscoped by pool. Resolved as part of the pool-scoped-roles rework below: `seasonId` is now optional on `POST /admin/broadcast` — admin can omit it (everyone, unchanged) or supply one (scoped to that pool); a non-admin pool commissioner must supply their own pool and can't omit it. Verified live: admin-no-seasonId reaches everyone, a pool commissioner scoped to their own pool succeeds, the same commissioner omitting `seasonId` or targeting a different pool both 403.
- [x] Read-side endpoints didn't check pool membership at all — any authenticated user could view any pool's data by ID regardless of whether they'd joined it: `GET /weeks/:id`, `GET /weeks/:id/picks/summary`, `GET /weeks/:id/standings`, `GET /seasons/:id/standings`. Fixed: new `requirePoolMember` primitive in [middleware.ts](backend/src/lib/middleware.ts) (admin bypasses, otherwise requires *any* `SeasonMembership` — player or commissioner — unlike `requirePoolCommissioner` which requires the commissioner role specifically), wired into all four.
